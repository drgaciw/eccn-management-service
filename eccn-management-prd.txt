ECCN Management Service - Product Requirements Document (PRD)

1. Project Overview
- Purpose: Provide a centralized service to manage Export Control Classification Numbers (ECCNs), related product data, and export control compliance workflows including crypto classification, licensing dashboards, and screening support.
- Scope: Backend Spring Boot service with Angular UI. Includes CRUD for ECCNs and Products, ECCN search and validation, crypto classification utilities, export control dashboards drawing from MongoDB collections, and supporting endpoints for workflows.
- Business Objectives:
  - Ensure correct ECCN assignment for products/modules and maintain history and relationships.
  - Support compliance decisions (licensing, screening, country restrictions) via dashboards and data APIs.
  - Provide auditable workflows for product version classification and deprecation/supersession of ECCNs.
  - Offer APIs and UI to integrate with internal compliance processes and tools.

2. Functional Requirements
2.1 ECCN Management
- Create, read, update, delete ECCN records
- Search by commodity code, category, encryption-related flag
- Retrieve ECCNs by EAR controls, data analytics capabilities, and financial software flags
- Manage ECCN lifecycle: deprecate with reason, replacement ECCN, track history/related ECCNs
- Validate ECCN format (regex 5 uppercase alphanumeric)

2.2 Product Classification Workflow
- Create/update products with versions, encryption indicators, and features
- Track version classification status (PENDING/CLASSIFIED)
- Mark a product version as CLASSIFIED
- Query products by status, search by name, list pending classifications
- Emit product-related events for downstream processing

2.3 Cryptography Classification
- Determine ECCN (e.g., 5D992 vs 5D002) based on algorithm, key length, and mass market characteristics
- Classify crypto algorithm/mode and evaluate weak modes
- De minimis assessment and ERN derivation for products with encryption
- Library-based analysis helpers (algorithm/key length/mass market heuristics)

2.4 Export Control Dashboard & Data Access
- Provide dashboard metrics: pending transactions, expiring licenses, pending screenings, recent transactions, license utilization, transactions by country, and compliance alerts
- Expose supporting collections: export_licenses, country_restrictions, customers, export_transactions

2.5 UI Navigation (Angular)
- Routes: /dashboard, /eccn, /eccn/new, /eccn/:id, /classifications (list/new/detail), /export-control, /pending-approvals, /test-material
- Components for ECCN listing/detail, classification workflows, export control tabs (license management, country controls, screening, documentation, compliance, audits, regulatory updates), dashboard widgets

3. Technical Architecture
- Backend: Spring Boot 3.4.4 (Java 21), Spring Data MongoDB, Spring Security, Springdoc OpenAPI, Actuator, Spring Cloud (loadbalancer, circuitbreaker-resilience4j), Lombok, Caffeine (cache), DevTools
- Database: MongoDB; collections used directly or via repositories
  - eccn_codes (Eccn), products (Product), export_controls (ExportControl)
  - Also referenced as documents: export_transactions, export_licenses, customers, country_restrictions
- Frontend: Angular (standalone components), Angular Material, NgRx store/effects, HTTP interceptor, routing
- Containerization: Dockerfile builds JAR image; docker-compose provides MongoDB and service
- Configuration: application.properties; security config; actuator exposure; swagger
- Logging: INFO default, package DEBUG; LiveReload in dev

4. API Specifications
Authentication
- HTTP Basic Auth required for most endpoints
- In-memory default user: admin/admin with roles ADMIN, USER
- Authorization rules:
  - Public: /swagger-ui/**, /v3/api-docs/**, /error, /health, /info
  - /actuator/**: ROLE_ADMIN
  - /api/** GET: authenticated
  - /api/** POST/PUT/PATCH: ROLE_ADMIN or ROLE_EDITOR
  - /api/** DELETE: ROLE_ADMIN

Base URL
- Default port 8080; API base /api

4.1 ECCN Core API (EccnApiController) - /api/eccn
- GET /api/eccn -> 200 List<{ id, commodityCode, description, category, encryptionRelated }>
- GET /api/eccn/{id} -> 200 Eccn | 404
- GET /api/eccn/code/{commodityCode} -> 200 List<Eccn>
- GET /api/eccn/category/{category} -> 200 List<Eccn>
- GET /api/eccn/encryption -> 200 List<Eccn>
- GET /api/eccn/search?term=abc -> 200 List<Eccn>
- POST /api/eccn body: Eccn -> 200 Eccn
- PUT /api/eccn/{id} body: Eccn -> 200 Eccn | 404
- DELETE /api/eccn/{id} -> 204 | 404
Notes: Eccn model fields in section 5. Exists alongside /api/eccn-list endpoints (see 4.3).

4.2 ECCN Operations API (EccnController) - /api/eccn-operations
- POST /api/eccn-operations body: Eccn -> 200 Eccn (validates commodityCode format)
- PUT /api/eccn-operations/{id} body: Eccn -> 200 Eccn
- GET /api/eccn-operations/commodity-code/{commodityCode} -> 200 List<Eccn>
- GET /api/eccn-operations/financial-software -> 200 List<Eccn>
- GET /api/eccn-operations/data-analytics?capabilities=a,b -> 200 List<Eccn>
- GET /api/eccn-operations/ear-controls?earControls=a,b -> 200 List<Eccn>
- GET /api/eccn-operations/status -> 200 text (service status)

4.3 ECCN List API (EccnListController) - /api/eccn-list
- GET /api/eccn-list -> 200 List<Eccn>
- GET /api/eccn-list/{id} -> 200 Eccn | 404
- GET /api/eccn-list/search?term=abc -> 200 List<Eccn>
- GET /api/eccn-list/category/{category} -> 200 List<Eccn>
- GET /api/eccn-list/encryption-related -> 200 List<Eccn>
- POST /api/eccn-list body: Eccn -> 200 Eccn (rejects if id exists)
- PUT /api/eccn-list/{id} body: Eccn -> 200 Eccn | 404
- DELETE /api/eccn-list/{id} -> 204 | 404

4.4 Product API (ProductController) - /api/products
- POST /api/products body: Product -> 200 Product (sets status=ACTIVE; versions[*].classificationStatus=PENDING)
- PUT /api/products/{id} body: Product -> 200 Product (preserves existing version classification status; emits events)
- GET /api/products/status/{status} -> 200 List<Product>
- GET /api/products/search?name=abc -> 200 List<Product>
- GET /api/products/pending-classification -> 200 List<Product>
- PATCH /api/products/{productId}/versions/{versionNumber}/mark-classified -> 204

4.5 Crypto Classification API (CryptoClassificationController) - /api/crypto-classification
- POST /api/crypto-classification/classify?keyLength=256&algorithm=AES&isMassMarket=false -> 200 String (e.g., "ECCN 5D992", "ECCN 5D002", or "Not classified")

4.6 Export Control API (ExportControlController) - /api/export-control
- GET /api/export-control -> 200 List<ExportControl>
- GET /api/export-control/{id} -> 200 ExportControl | 404
- GET /api/export-control/dashboard -> 200 Map dashboard data summary
- GET /api/export-control/licenses -> 200 List<Document> (license objects with id, number, type, dates, utilization)
- GET /api/export-control/licenses/{id} -> 200 Document | 404
- GET /api/export-control/country-restrictions -> 200 List<Document>
- GET /api/export-control/customers -> 200 List<Document>
- GET /api/export-control/transactions -> 200 List<Document>
Notes: These read directly from MongoDB collections and transform _id to id.

5. Data Models
5.1 Eccn (collection: eccn_codes)
- id: string (MongoDB ObjectId)
- commodityCode: string (validated: ^[0-9A-Z]{5}$)
- description: string
- category: string
- encryptionRelated: boolean
- encryptionControlNumber: string (e.g., 5D002)
- encryptionAlgorithms: string[]
- financialSoftware: boolean
- supportedPaymentMethods: string[]
- fraudDetectionCapabilities: boolean
- dataAnalytics: boolean
- analyticsCapabilities: string[]
- applicableEARControls: string[]
- exceptions: string[]
- deprecated: boolean
- deprecationReason: string
- replacementEccnId: string
- createdDate: Date
- modifiedDate: Date
- relatedEccns: string[]
- history: EccnHistoryEntry[] { changeDate: Date, changedBy: string, changeDescription: string }

5.2 Product (collection: products)
- id: string
- name: string
- description: string
- features: string[]
- versions: VersionRelease[] { versionNumber: string, releaseDate: string, encryptionLibraries: string[], classificationStatus: "PENDING"|"CLASSIFIED" }
- status: string (e.g., ACTIVE, DEPRECATED)
- usContentPercentage: number
- militaryUse: boolean
- controlledCountry: boolean
- encryptionEnabled: boolean

5.3 ExportControl (collection: export_controls)
- id: string
- moduleName: string
- earClassification: string
- jurisdictionClassifications: Map<jurisdiction, classification>
- conflictingJurisdictions: string[]
- unifiedClassification: string (most restrictive)
- complianceRequirements: string[]
- requiresSpecialHandling: boolean

5.4 Supporting Collections (as documents accessed via controller)
- export_transactions: transactions with customer, destination, products, license, screening result, documentation status, status, values, dates
- export_licenses: id, licenseNumber, type, issue/expiration dates, products, countries, value limits/used, status, attachments
- customers: id, name, address, country, screeningStatus, dates, red flags
- country_restrictions: id, countryCode, countryName, restrictionLevel, requiresLicense, embargoType, notes, lastUpdated

6. User Interface Requirements (Angular)
- Landing page with links to Dashboard, ECCN, Classification Workflow
- ECCN List (/eccn): table/grid of ECCNs; filter/search; navigation to detail (/eccn/:id); create (/eccn/new)
- ECCN Detail: forms (enhanced/optimized/validation variants) to create/edit; fields match Eccn model; validation feedback
- Classifications section (/classifications): list/create/detail for classification workflow (mock and test components exist)
- Export Control (/export-control): tabbed UI
  - Dashboard: widgets for counts, license utilization, transactions by country, alerts
  - License Management, Country Controls, End-User Screening, Export Documentation, Compliance, Audit, Regulatory Updates components present for navigation/content
- Pending Approvals (/pending-approvals): list of items awaiting approval
- Test Material (/test-material): developer/test utilities
- State Management: NgRx store/effects for ECCN and classification workflows; HTTP interceptor for API calls; Angular Material components for UI/UX

7. Security Requirements
- Authentication: HTTP Basic; default admin/admin for dev; passwords encoded with BCrypt
- Authorization: Role-based as per SecurityFilterChain
  - Admin can access actuator and all mutating operations; Editor (if provisioned) can POST/PUT/PATCH; Users can read
- Transport: SSL trust-all flags present for dev; production must enforce proper TLS and trust stores
- Public Endpoints: Swagger UI and OpenAPI docs exposed for discovery; ensure docs exclude sensitive data

8. Integration Requirements
- MongoDB 7.x required; connection string configurable (env SPRING_DATA_MONGODB_URI). Default dev points to localhost:27018 (docker-compose mapped) with authSource=admin user root/secret
- Optional service discovery (Eureka) properties present; not required if not running Eureka
- Resilience4j circuit breaker annotations used in EccnService for history retrieval (fallback returns empty list)
- Potential AI model integration via AutomatedClassificationToolService.AIModel interface (pluggable for advanced classification)

9. Performance Requirements
- Typical API responses within 300ms under normal load; dashboard operations may vary based on Mongo aggregation patterns
- Throughput designed for internal compliance teams (tens to hundreds of requests/minute); scale horizontally via stateless containers
- MongoDB indices recommended (not defined in code) on fields: commodityCode, category, encryptionRelated, versions.classificationStatus, moduleName, unifiedClassification
- Caching currently disabled (cache.type=none); can enable Caffeine if needed for read-heavy endpoints

10. Deployment Requirements
- Dockerfile runs pre-built JAR (OpenJDK 21) and exposes port 8080
- docker-compose.yml provisions:
  - mongodb: mongo:7.0, user root/secret, mapped port 27018:27017
  - eccn-management-service: builds from repo, exposes 8080, env SPRING_DATA_MONGODB_URI to reach mongodb service
- Environments:
  - Dev: local with docker-compose; application.properties points to localhost:27018
  - Test: application-test.properties uses local mongodb testdb (no auth) for tests
  - Production: provide secure Mongo URI, credentials, TLS, secrets management; restrict actuator; define real users/roles
- Observability: Actuator endpoints enabled; health requires ADMIN; logs at INFO/DEBUG; add metrics and tracing as needed
- API Docs: Springdoc OpenAPI at /swagger-ui.html and /v3/api-docs

11. Non-Functional Considerations
- Reliability: Use circuit breakers for external/DB if needed; handle Mongo downtime gracefully with fallbacks
- Auditability: Maintain ECCN history; emit Product events; consider persistence of events or audit logs in future
- Maintainability: Clear separation of controllers/services/repositories; use Lombok to reduce boilerplate; Angular standalone components
- Security Hardening (prod):
  - Replace in-memory users with external IdP or user store
  - Enforce TLS; remove trust-all settings; secure actuator (IP allowlist, separate management port)
  - Input validation on controllers; rate limiting if exposed broadly

12. Open Issues and Assumptions
- Duplicate ECCN CRUD surfaces (/api/eccn and /api/eccn-list) and operational endpoints (/api/eccn-operations) overlap; consolidate or define responsibility boundaries
- Dashboard relies on collections not fully modeled in code; define schemas and ownership for export_* and customers collections
- Some Spring Cloud/Hystrix/Eureka settings are present but not actively used; clarify environment expectations
- Angular services include mock data flags; production must set environment.useRealApi=true and base apiUrl
- Additional endpoints referenced by Angular EccnService (history, related, validate, deprecate) are not fully implemented in backend; plan implementation or adjust UI
